Problem Solving 01

화이트 스크린 및 메모리 증가 문제 해결

Problem

24시간 상시 가동 환경에서 일정 시간 주기로 화면이 하얗게 멈추고, 실행 시간이 길어질수록 메모리가 지속 증가했습니다.

Analyze

Heap Snapshot, Allocation Timeline, PID별 메모리를 추적하며 JS Heap 외부의 Electron renderer memory 증가까지 분석 범위를 넓혔습니다.

Action

WebSocket·Worker·Timer·RAF·Observer cleanup, ImageBitmap.close(), rolling window, backpressure, ECharts 축 갱신 구조 개선을 적용했습니다.

Result

24시간 미만 주기의 화이트 스크린을 해소하고 renderer·WebSocket·백엔드 장애 발생 시 자동 복구 및 관제 상태 복원 구조를 확보했습니다.

세부 조치

  • 실시간 데이터에 고정 크기 rolling window를 적용해 무제한 누적 방지
  • 열화상 프레임 처리에 최신 프레임 우선 backpressure를 적용해 비동기 디코딩 중첩 방지
  • X축을 고정 상대 좌표 범위로 전환하고 데이터 좌표만 최신 시각 기준으로 변환해 ECharts 축 모델 반복 갱신 방지
  • 실제 시간 라벨을 ECharts Canvas에서 React DOM으로 분리하고 고정 DOM 노드 재사용
  • React·Electron 오류를 통합 수집해 IPC 기반으로 백엔드에 전달하고, fallback UI와 지연 새로고침 적용
  • Electron main process에서 renderer 종료 또는 응답 없음 상태를 감지해 reload 및 BrowserWindow 재생성 수행

Problem Solving 02

JavaScript → TypeScript 전환 및 컴포넌트 구조 개선

Problem

천장형·바닥형 관제 통합 후 기능과 데이터 흐름이 복잡해졌고, 타입 부재와 책임이 혼재된 컴포넌트 구조로 유지보수 비용이 증가했습니다.

Action

핵심 도메인 타입을 정의하고, 단일 책임 원칙에 맞춰 컴포넌트 역할과 폴더 구조를 재설계했습니다.

Result

타입 관련 런타임 오류를 4건에서 0건으로 줄이고, WebSocket 상태 변경에 따른 리렌더링 전파 범위를 축소했습니다.

구조 개선

  • API·WebSocket 데이터와 컴포넌트 사이의 데이터 계약을 명시
  • 단일 WebSocket Context를 역할별 Context로 분리해 필요한 상태만 구독하도록 개선
  • 기능 변경 시 확인해야 하는 코드 범위와 의존 관계를 명확하게 정리

Problem Solving 03

API 아키텍처 재설계 및 TanStack Query 도입

Problem

메인 페이지에 9개 도메인의 API 호출과 서버 상태 관리가 집중되어 중복 요청, 상태 불일치, prop drilling, 예외 처리 불일치가 발생했습니다.

Action

공통 httpClient, service 계층, query hook을 분리하고 Query Cache 기반 서버 상태 관리 구조로 전환했습니다.

Result

API 관련 코드 약 500줄을 줄이고 fetch 함수·상태 setter prop drilling, JSON.stringify 기반 직접 동기화 로직을 제거했습니다.

표준화 항목

  • timeout, 응답 parsing, 공통 에러 처리를 httpClient로 통합
  • 서버 raw response 타입과 프론트엔드 domain model을 분리
  • snake_case → camelCase 변환을 service 계층에 캡슐화
  • polling, request deduplication, mutation 이후 invalidateQueries를 Query 계층으로 이동
  • structural sharing으로 변경되지 않은 데이터 참조를 유지하고 깊은 비교 로직 제거

Problem Solving 01

고해상도 지도 Canvas 렌더링 병목 해결

Problem

마우스 드래그·줌 과정에서 고해상도 지도와 다수 노드를 동시에 렌더링하며 프레임 저하와 Painting 비용 증가가 발생했습니다.

Analyze

Performance 분석 결과 JavaScript 실행보다 고해상도 이미지 반복 Painting이 주요 병목이었고, 정적 지도와 동적 요소의 갱신 주기 차이가 재그리기를 키웠습니다.

Action

ImageBitmap 캐싱, Multi-Canvas 레이어 분리, 오프스크린 Canvas 밉매핑, WebP 변환과 좌표 보정을 적용했습니다.

Result

지도 로딩 시간은 약 10s → 3s, Painting Time은 4,300ms → 170ms, Main Thread Long Task는 51회 → 7회로 개선했습니다.

Problem Solving 02

대용량 FCD 처리 최적화 및 전체 적재 OOM 개선

Problem

SUMO에서 생성되는 수 GB 규모 FCD XML을 전체 변환·적재하면서 약 400초 처리 시간이 발생했고, Unity WebGL 메모리 한계로 OOM이 발생했습니다.

Analyze

포맷 경량화만으로는 브라우저 메모리 한계를 해결하기 어려워, 필요한 시점의 데이터만 조회·전송하는 온디맨드 구조로 문제를 재정의했습니다.

Action

NDJSON 기반 스트리밍 구조로 전환하고, 시뮬레이션 시간과 파일 byte offset을 매핑한 인덱스 테이블을 구축했습니다.

Result

처리 시간을 약 400s → 85s로 78.7% 단축하고, FCD 전체 데이터를 Unity WebGL 메모리에 적재하면서 발생하던 OOM을 제거했습니다.

처리 개선 단계

  • 포맷 및 필드 경량화로 약 400s → 115s 단축
  • 인덱스 기반 조회 구조 적용으로 115s → 85s 추가 단축
  • 요청 시 파일 전체를 순차 탐색하지 않고 byte offset으로 필요한 데이터 구간을 직접 조회
  • Python으로 데이터 처리 파이프라인을 구현하고 Java 백엔드에서 활용할 수 있도록 구조와 처리 방식 인계
