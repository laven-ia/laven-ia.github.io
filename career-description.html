Problem Solving 01

화이트 스크린 및 메모리 증가 문제 해결

Problem

24시간 상시 가동되는 현장 환경에서 일정 시간 주기로 화면이 하얗게 멈추는 장애가 발생했고, 실행 시간이 길어질수록 메모리가 지속적으로 증가해 장기 관제가 어려웠습니다.

Analyze

단순 React 상태나 JavaScript 객체만으로는 원인이 확인되지 않아 JS Heap, 비동기 작업, 외부 리소스 생명주기, Electron renderer memory, ECharts 렌더링 경로까지 단계적으로 분석 범위를 넓혔습니다.

Action

외부 리소스 cleanup, ImageBitmap.close(), rolling window, 최신 프레임 우선 backpressure, ECharts X축 갱신 구조 개선, 오류 수집 및 Electron 자동 복구 절차를 적용했습니다.

Result

24시간 미만 주기로 발생하던 화이트 스크린을 해소하고 JavaScript Heap 및 Electron renderer memory의 지속적인 우상향 현상을 안정화했습니다.

분석 과정

  • Chrome DevTools의 Heap Snapshot · Allocation Timeline으로 JavaScript 객체의 생성·해제 추이와 Retainer 경로를 분석하고, 비동기 작업 및 외부 리소스의 생명주기를 점검
  • JavaScript Heap 관련 누수 요소를 정리한 이후에도 프로세스 메모리가 지속적으로 증가하는 현상을 확인해 JS Heap 외부로 분석 범위 확대
  • Windows 작업 관리자의 PID별 활성 개인 메모리 · 커밋 크기를 추적하며 Electron renderer memory 증가 문제로 범위를 좁힘
  • 컴포넌트와 렌더링 기능을 단계적으로 비활성화해 비교한 결과, ECharts의 반복적인 setOption() 실행 경로에서 renderer memory가 증가하는 현상 확인
  • axis · series · animation을 각각 분리해 검증하며 동적 X축 시간 formatter의 반복 렌더링 경로까지 원인을 세분화

세부 조치

  • 비동기 요청 취소, WebSocket·Worker·Timer·RAF·Observer 등 외부 리소스 cleanup을 정비하고 ImageBitmap.close()를 적용해 컴포넌트 종료 이후 남는 작업과 네이티브 이미지 리소스를 명시적으로 해제
  • 실시간 데이터에 고정 크기 rolling window를 적용해 무제한 누적 방지
  • 열화상 프레임 처리에 최신 프레임 우선 backpressure를 적용해 비동기 디코딩 중첩 방지
  • X축을 고정 상대 좌표 범위로 전환하고 데이터 좌표만 최신 시각 기준으로 변환해 ECharts 축 모델 반복 갱신 방지
  • 실제 시간 라벨을 ECharts Canvas에서 React DOM으로 분리하고 고정 DOM 노드 재사용
  • 시간 라벨 갱신 주기를 초 단위로 제한하고 메모이제이션 적용
  • WebSocket 재연결을 고정 주기 방식에서 최대 대기 시간을 둔 지수 백오프 방식으로 변경
  • React·Electron 오류를 통합 수집해 IPC 기반으로 백엔드에 전달하고, fallback UI와 지연 새로고침 적용
  • Electron main process에서 renderer 종료 또는 응답 없음 상태를 감지해 reload 및 BrowserWindow 재생성 수행
  • localStorage 기반 상태 영속화를 적용하여 renderer 복구 후 기존 관제 상태 복원

결과

  • 24시간 미만 주기로 발생하던 화이트 스크린 현상 해소
  • JavaScript Heap 및 Electron renderer memory의 지속적인 우상향 현상 안정화
  • renderer · WebSocket · 백엔드 장애 발생 시 자동 복구 및 관제 상태 복원 구조 확보
  • 프론트엔드 오류를 백엔드로 수집하는 체계를 구축해 장시간 운영 환경의 장애 진단 범위 확대

Problem Solving 02

JavaScript → TypeScript 전환 및 컴포넌트 구조 개선

Problem

천장형·바닥형 관제 시스템 통합 과정에서 기능과 데이터 흐름이 복잡해졌고, JavaScript의 타입 부재와 책임이 혼재된 컴포넌트 구조로 유지보수 문제가 발생했습니다.

Analyze

동일 구조에서 신규 기능을 계속 추가할 경우 런타임 오류와 컴포넌트 간 결합도가 함께 증가할 것으로 판단해 타입 안정성 확보와 책임 분리를 구조 개선의 우선순위로 잡았습니다.

Action

JavaScript 코드를 TypeScript로 전환하고, 핵심 도메인 타입 정의, 컴포넌트 역할과 폴더 구조 재설계, WebSocket Context 역할별 분리를 진행했습니다.

Result

타입 관련 런타임 오류를 4건에서 0건으로 줄이고, WebSocket 상태 변경에 따른 리렌더링 전파 범위를 축소했습니다.

문제 상황

  • 기능 변경 시 관련 로직이 여러 컴포넌트에 분산되어 변경 영향 범위와 오류 발생 지점 추적이 어려움
  • API · WebSocket 데이터의 타입이 보장되지 않아 예상하지 못한 런타임 오류 발생
  • 실시간 데이터를 하나의 WebSocket Context에서 관리해 특정 데이터 변경 시 해당 데이터를 사용하지 않는 컴포넌트까지 함께 리렌더링

구조 개선

  • TypeScript 전환을 통해 컴파일 단계에서 타입 오류 검증
  • 핵심 비즈니스 도메인의 타입을 정의해 API · WebSocket 데이터와 컴포넌트 사이의 데이터 계약을 명시
  • 단일 책임 원칙을 기준으로 컴포넌트 역할과 폴더 구조 재설계
  • 단일 WebSocket Context를 역할별 Context로 분리해 필요한 상태만 구독하도록 개선
  • 컴포넌트와 도메인별 책임을 분리해 기능 변경 시 확인해야 하는 코드 범위와 의존 관계를 명확하게 개선
  • WebSocket 상태 변경 시 전체 Context 소비자가 함께 갱신되던 구조를 분리해 리렌더링 전파 범위 축소

Problem Solving 03

API 아키텍처 재설계 및 TanStack Query 도입

Problem

메인 페이지에 9개 도메인의 API 호출과 서버 상태 관리가 집중되어 중복 요청, 상태 불일치, prop drilling, 예외 처리 불일치가 발생했습니다.

Analyze

개별 fetch 코드를 정리하는 것만으로는 중복 요청, 상태 동기화, 에러 처리, 데이터 변환 문제를 함께 해결하기 어려워 HTTP 통신 → API 응답 변환 → 서버 상태 관리의 책임을 계층별로 분리하기로 결정했습니다.

Action

공통 httpClient, types/{domain}.api.ts → services → hooks/queries 구조, TanStack Query 기반 Query Cache 서버 상태 관리 구조를 도입했습니다.

Result

API 관련 코드 약 500줄을 줄이고 fetch 함수·상태 setter prop drilling, JSON.stringify 기반 직접 동기화 로직을 제거했습니다.

문제 상황

  • 각 API에서 AbortController, timeout, try-catch, snake_case → camelCase 변환 로직이 반복
  • 서버 응답 변경 여부를 확인하기 위해 JSON.stringify(prev) === JSON.stringify(next) 기반 깊은 비교 반복
  • fetch 함수와 상태 setter가 prop drilling으로 전달되며 컴포넌트 간 결합도 증가
  • 동일 서버 데이터를 여러 컴포넌트에서 개별 호출해 중복 요청 및 상태 불일치 가능성 존재
  • API마다 에러 응답 처리 방식이 달라 예외 처리의 일관성 부족

표준화 항목

  • timeout, 응답 parsing, 공통 에러 처리를 httpClient로 통합
  • HttpError 커스텀 에러를 통해 status와 response body 기반 예외 처리 방식 통일
  • 서버 raw response 타입과 프론트엔드 domain model을 분리
  • HTTP 호출과 snake_case → camelCase 변환을 service 계층에 캡슐화
  • query hook으로 데이터 fetching과 서버 상태 관리 책임을 컴포넌트 외부로 분리
  • queryKey 기반 캐시를 적용해 동일 서버 데이터를 여러 컴포넌트에서 공유
  • polling, request deduplication, mutation 이후 invalidateQueries를 Query 계층으로 이동
  • structural sharing으로 변경되지 않은 데이터 참조를 유지하고 깊은 비교 로직 제거
  • 서버 상태를 Query Cache에서 공유하도록 변경해 fetch 함수 · 상태 setter의 prop drilling 제거
  • API 응답 타입 · 데이터 변환 · 에러 처리 방식을 도메인별 동일한 구조로 표준화

결과

  • 메인 페이지 기준 API 관련 코드 약 500줄 감축
  • 컴포넌트 내부의 직접 fetch 및 반복적인 API 보일러 플레이트 제거
  • 동일 query를 여러 컴포넌트가 사용하는 경우 개별 fetch하던 구조 제거
  • JSON.stringify 기반 직접 상태 비교 및 동기화 로직 제거

Problem Solving 01

고해상도 지도 Canvas 렌더링 병목 해결

Problem

마우스 드래그·줌 과정에서 고해상도 지도와 다수 노드를 동시에 렌더링하며 심각한 프레임 저하가 발생했고, 줌아웃 시 원본 이미지를 매 프레임 축소하면서 반복적인 이미지 리샘플링 및 Painting 비용이 증가했습니다.

Analyze

Chrome DevTools Performance 분석 결과 JavaScript 실행 시간보다 고해상도 이미지의 반복 Painting 비용이 주요 병목이었고, 정적 지도와 동적 인터랙션 요소를 동일 Canvas에서 그리는 구조가 불필요한 재그리기를 발생시킨다고 판단했습니다.

Action

ImageBitmap 캐싱, 정적 지도와 동적 인터랙션 레이어를 분리한 Multi-Canvas 구조, 오프스크린 Canvas 기반 밉매핑, WebP 변환과 좌표·offset 보정을 적용했습니다.

Result

지도 로딩 시간은 약 10s → 3s, Painting Time은 4,300ms → 170ms, Main Thread Long Task는 51회 → 7회로 개선했습니다.

세부 조치

  • 지도 이미지를 ImageBitmap으로 디코딩해 useRef에 캐싱하고, 언마운트 시 .close()를 호출해 이미지 리소스를 명시적으로 해제
  • 정적 지도와 동적 인터랙션 레이어를 분리한 Multi-Canvas 구조를 적용해 갱신이 필요한 영역만 다시 렌더링하도록 개선
  • 50%·25% 축소 이미지를 오프스크린 Canvas에 사전 생성하고 줌 배율에 따라 적절한 해상도의 이미지를 선택하는 밉매핑 방식 설계
  • PNG를 WebP로 변환하고 quality=75 손실 압축을 적용해 초기 이미지 로딩 비용 축소
  • WebP 변환 과정에서 해상도가 자동 조정되며 기존 노드 좌표와 불일치하는 문제를 발견하고, 원본 대비 해상도 비율을 기준으로 좌표와 offset을 동적으로 보정

Problem Solving 02

대용량 FCD 처리 최적화 및 전체 적재 OOM 개선

Problem

SUMO에서 생성되는 FCD XML 데이터가 수 GB 규모로 증가하면서 전체 변환·적재 방식에서 약 400초의 처리 시간이 발생했고, 변환된 전체 데이터를 Unity WebGL에 적재할 경우 브라우저 메모리 한계로 OOM이 발생했습니다.

Analyze

XML → JSON 변환과 필요 필드 선별로 데이터 크기를 줄였지만 Unity WebGL OOM은 지속되어, 전체 데이터를 보유하는 방식 자체를 제거하고 필요한 시뮬레이션 시점의 데이터만 공급하는 온디맨드 스트리밍 구조로 문제를 재정의했습니다.

Action

XML 전체 변환·적재 방식에서 NDJSON 기반 스트리밍 구조로 전환하고, 시뮬레이션 시간과 파일 내부 byte offset을 매핑한 인덱스 테이블을 사전에 구축했습니다.

Result

처리 시간을 약 400s → 85s로 78.7% 단축하고, FCD 전체 데이터를 Unity WebGL 메모리에 적재하면서 발생하던 OOM을 제거했습니다.

처리 개선 단계

  • 포맷 및 필드 경량화로 약 400s → 115s 단축
  • 인덱스 기반 조회 구조 적용으로 115s → 85s 추가 단축
  • 필요한 시뮬레이션 시점의 데이터만 WebSocket으로 전달하는 온디맨드 데이터 공급 구조 구현
  • 시뮬레이션 시간과 파일 내부 byte offset을 매핑한 인덱스 테이블을 사전에 구축
  • 요청 시 파일 전체를 순차 탐색하지 않고 byte offset으로 필요한 데이터 구간을 직접 조회
  • 전체 적재 방식에서 필요한 시점의 데이터만 공급하는 구조로 전환해 FCD 데이터 규모 증가에 따른 클라이언트 메모리 부담 완화
  • Python으로 데이터 처리 파이프라인을 구현하고 Java 백엔드에서 활용할 수 있도록 구조와 처리 방식 인계
