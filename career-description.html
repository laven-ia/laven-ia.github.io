Problem Solving 01

24시간 관제 환경의 화이트 스크린 및 메모리 증가 원인 추적

Problem

상시 가동되는 Electron 기반 관제 애플리케이션에서 메모리가 지속적으로 증가하고, 24시간 이내 주기로 화면이 하얗게 멈추는 장애가 발생했습니다.

Analyze

Chrome DevTools의 Heap Snapshot과 Allocation Timeline으로 JavaScript 객체의 생성, 해제 추이와 Retainer 경로를 확인하고, Windows 작업 관리자의 PID별 메모리를 추적해 Electron renderer 프로세스로 분석 범위를 확장했습니다.

Action

ECharts의 반복적인 setOption 실행 경로와 동적 시간축 formatter를 원인 영역으로 좁히고, 시간축 구조 변경, cleanup 정리, rolling window, backpressure, Electron 복구 구조를 적용했습니다.

Result

24시간 미만 주기로 발생하던 화이트 스크린 현상을 해소하고, JavaScript Heap 및 Electron renderer memory의 지속적인 우상향을 안정화했습니다.

세부 개선

  • 실제 시각에 따라 변경되던 X축을 고정 상대 좌표 범위로 전환하고 데이터 좌표만 최신 시각 기준으로 변환했습니다.
  • 실제 시간 라벨을 ECharts Canvas에서 React DOM으로 분리해 고정 노드를 재사용하고 갱신 주기를 초 단위로 제한했습니다.
  • 비동기 요청, WebSocket, Worker, Timer, RAF, Observer cleanup을 정리하고 ImageBitmap.close()로 네이티브 리소스를 해제했습니다.
  • 실시간 데이터에는 고정 크기 rolling window를 적용하고 열화상 프레임 처리에는 최신 프레임 우선 backpressure를 적용했습니다.
  • renderer 종료와 응답 없음 상태를 main process에서 감지해 단계적 reload 및 BrowserWindow 재생성을 수행하도록 했습니다.

Problem Solving 02

프론트엔드 API 계층 및 데이터 관리 구조 재설계

Problem

메인 페이지에 여러 기능 영역의 API 호출과 서버 상태 관리 로직이 집중되어 있었고, 상태와 fetch 로직을 상위 컴포넌트에서 props로 하위 계층까지 전달해야 했습니다.

Analyze

핵심 문제를 서버 상태의 소유 위치가 컴포넌트 트리에 종속된 점으로 보고, API 호출과 서버 상태를 UI 컴포넌트에서 분리하는 방향으로 구조를 재설계했습니다.

Action

httpClient, types/{domain}.api.ts, services, hooks/queries로 계층을 분리하고 TanStack Query의 Query Cache 중심으로 서버 상태를 공유하는 구조를 적용했습니다.

Result

메인 페이지 기준 API 관련 코드 약 500줄을 감축하고, fetch 함수와 상태 setter의 prop drilling을 제거했습니다.

세부 개선

  • timeout, 응답 parsing, 공통 에러 처리를 httpClient에 통합하고 HttpError로 예외 처리 방식을 표준화했습니다.
  • 서버 raw response와 프론트엔드 domain model을 분리하고 snake_case에서 camelCase 변환을 service 계층에 캡슐화했습니다.
  • queryKey 기반 캐시를 통해 컴포넌트 위치와 관계없이 동일 서버 상태를 공유하도록 변경했습니다.
  • polling, request deduplication, mutation 이후 invalidateQueries를 Query 계층으로 이동했습니다.
  • structural sharing을 활용해 JSON.stringify 기반 직접 깊은 비교와 상태 동기화 로직을 제거했습니다.

Problem Solving 03

실시간 스트리밍 생명주기 및 송출 안정성 개선

Problem

실제 시청자가 있는데도 스트림이 종료되어 영상이 재연결되는 문제가 발생했고, MediaMTX 로그에서는 RTP packet loss와 processing error가 반복되었습니다.

Analyze

프론트엔드 heartbeat가 브라우저 타이머 지연, 컴포넌트 생명주기, 요청 취소, 서버 처리 지연에 영향을 받아 실제 reader 상태와 어긋날 수 있음을 확인했습니다.

Action

MediaMTX가 직접 감지하는 reader 연결 상태를 스트림 생명주기 기준으로 변경하고, runOnDemand, runOnRead, runOnUnread 이벤트를 서버 상태와 연동했습니다.

Result

시청 중인 스트림이 heartbeat 누락으로 종료되던 문제를 해소하고, 스트림 등록, 기동, reader 감지, 종료 흐름을 일원화했습니다.

세부 개선

  • /register-stream에서 RTSP 정보를 사전 등록하고, 실제 시청 또는 해상도 조회 시에만 FFmpeg를 기동했습니다.
  • 해상도 조회 시 스트림이 비활성 상태라면 등록된 RTSP 정보로 자동 기동하는 복구 경로를 구성했습니다.
  • FFmpeg에서 MediaMTX 구간의 RTSP/RTP transport를 조정하고, TCP 연결 실패 시 UDP로 fallback하도록 변경했습니다.
  • 관제 환경에서는 장시간 송출 안정성을 우선해 fMP4 기반 일반 HLS로 전환하고 segment duration을 조정했습니다.

Problem Solving 01

고해상도 지도 Canvas 렌더링 병목 개선

Problem

고해상도 지도 위에 다수의 노드를 표시하는 관제 화면에서 드래그, 줌 시 심각한 프레임 저하가 발생했습니다.

Analyze

Chrome DevTools Performance 분석 결과 JavaScript 실행보다 고해상도 이미지의 반복적인 Painting이 주요 병목임을 확인했습니다.

Action

정적 지도와 동적 인터랙션 요소를 Multi-Canvas 구조로 분리하고, 자주 사용하는 해상도의 이미지를 사전 생성, 캐싱해 재사용했습니다.

Result

지도 로딩 시간은 약 10초에서 3초로, Painting Time은 약 4,300ms에서 170ms로, Main Thread Long Task는 51회에서 7회로 개선했습니다.

세부 개선

  • 원본의 50%, 25% 축소 이미지를 Offscreen Canvas에 사전 생성하고 줌 배율에 따라 적절한 이미지를 선택했습니다.
  • PNG를 WebP quality 75로 변환해 초기 이미지 로딩 비용을 축소했습니다.
  • 이미지 해상도 변경으로 발생한 노드 좌표와 지도 위치 불일치를 원본 대비 해상도 비율 기준으로 offset 보정했습니다.

Problem Solving 02

대용량 FCD 처리 구조 개선 및 Unity WebGL OOM 해결

Problem

SUMO에서 생성되는 FCD XML이 수 GB 규모로 증가하면서 전체 변환에 약 400초가 소요됐고, 변환 데이터를 Unity WebGL에 모두 적재할 경우 브라우저 메모리 한계로 OOM이 발생했습니다.

Analyze

단순한 데이터 크기나 변환 성능보다 전체 데이터를 사전에 변환하고 클라이언트 메모리에 보관하는 구조 자체가 한계라고 판단했습니다.

Action

XML 전체 변환, 적재 방식에서 NDJSON 기반 스트리밍 처리 구조로 전환하고, 시뮬레이션 시간과 파일 byte offset을 매핑한 인덱스를 사전에 생성했습니다.

Result

FCD 처리 시간을 약 400초에서 85초로 약 79% 단축하고, 데이터 규모 증가에 따른 클라이언트 메모리 부담을 완화했습니다.

세부 개선

  • XML을 JSON으로 변환하고 시뮬레이션에 필요한 필드만 선별해 처리 시간을 약 400초에서 115초까지 단축했습니다.
  • 인덱스 기반 조회 구조를 적용해 115초에서 85초까지 추가 단축했습니다.
  • 요청마다 대용량 파일을 처음부터 탐색하지 않고 byte offset으로 필요한 구간만 직접 조회하도록 변경했습니다.
  • 필요한 시점의 데이터만 WebSocket을 통해 Unity WebGL로 전달하도록 구성했습니다.
  • Python으로 데이터 처리 파이프라인을 구현하고 Java 백엔드에서 이어서 활용할 수 있도록 처리 구조와 방식을 인계했습니다.
